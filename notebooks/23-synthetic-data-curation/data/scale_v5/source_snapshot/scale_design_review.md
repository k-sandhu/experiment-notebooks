# Scale-v5 orchestration review

**Result: no blocking issues found.** I reviewed the scale-v5 transport, dispatcher, orchestration, collector, and fixture contract without changing study code or making model calls. The review is also recorded in [scale_design_review.json](scale_design_review.json).

The fixed design is represented in the default configuration: 600 eligible original value failures, a 2,048-source collection cap, an initial 512-source tranche followed by complete 256-source tranches, and 96 audit cases. Only usable, schema-valid original answers with at least one incorrect typed value count toward accrual. After accrual stops, eligible IDs are selected by the predeclared random permutation with seed 255777, not by error severity. A cap shortfall freezes all eligible cases and is reported instead of silently extending the collection.

Audit source packs use their own seed, split, and index range. The pipeline freezes the selected collection IDs before it calls any audit cases. Audit outcomes remain separate from selection and never enter either intervention arm. The collector checks the original failure count only at completed chunk boundaries. The intervention phase is an explicit later command, and recovery statistics are computed only after every scheduled request has settled.

Each selected source receives one fresh attempt and one repair-package attempt. Both carry the same source and instruction input hash. Fresh requests have no feedback. Repair requests include the model's previous response and generic failed-field flags; the request builder does not pass gold answers, expected values, or calculation traces. The default four-worker dispatch randomizes arm order in four-request blocks containing both arms for two cases. Progress output reports only completion, arm, case ID, cache status and transport failure, not value scores or arm advantage.

The request cache is keyed by SHA256 of the complete canonical request. It stores the full request and raw CLI output, compressed as deterministic gzip JSON with atomic replacement. Source and input hashes are retained across the request plan, candidate rows, ledger and intervention checks. The CLI runner uses a fresh temporary working directory, read-only sandboxing, ignored user configuration and rules, disabled tools and plugins, and a timeout included in the hashed request. It records CLI events and does not claim to control internal service retries.

The fixture wrapper verifies frozen core hashes and runs the frozen evaluator, a separate SQL/Decimal audit, and a visible-text Fraction audit before creating source packs. Existing packs are checked against the declared count, seed, tier, split and index range. Prior-source overlap checks use case IDs and normalized semantic hashes, with temporary/checkpoint paths and response exports excluded. The collector defaults to offline replay; model calls require an explicit `--live` flag. Helper code is loaded in isolated namespaces rather than imported from the repository.

Metrics keep value errors separate from evidence-only, schema, unusable and transport outcomes. Audit metrics stay separate. The primary decision matches the preregistered rule: positive repair-minus-fresh value recovery and two-sided exact McNemar p < 0.05. The paired bootstrap interval and reconnect sensitivity are reported separately. The code records USD spend as unknown when the CLI does not provide a defensible charge.

One nonblocking configuration caveat: `max_workers` may be set to 1 or 2. In that case the dispatcher splits the prepared four-request blocks into smaller actual waves. The default is 4; lower concurrency still keeps the full paired arms fixed and does not expose outcomes before the phase completes. A run with lower concurrency should report the actual worker count and wave size from its frozen protocol.

I ran the scale fixture, experiment and transport mock suite with `python -m unittest discover -s authoring -p 'test_scale*.py' -v`. All 26 tests passed; the tests use mocked model responses and make no model calls.
