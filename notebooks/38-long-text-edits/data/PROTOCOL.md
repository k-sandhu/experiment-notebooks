## 2026-10-30: Amendment 1 (after 630 of 1,260 replies were seen)

Partial results from 630 generation replies showed the original `apply_patch` format producing
18 exact documents out of 87 replies with the `reference` applier. In 160 of the 258 chunks with
an `@@` anchor, that anchor was also one of the chunk's own context or removed lines, usually
not the first one. The reference search starts after the anchor, so those chunks cannot be
placed there, although 474 of 526 chunks' old sides occur exactly in the document. The original
instruction, `@@ a line just before the change, copied from the document`, invites a nearby line.
OpenAI's GPT-4.1 prompting guide, Appendix: Generating and Applying File Diffs, instead shows
three lines of context above and below a change and uses `@@` to name a containing class or
function when the context is not unique. For this document task, the equivalent is a section heading.

Added an eighth format, `apply_patch_openai`, with the wording specified verbatim in
[SPEC_PATCH_WORDING.md](protocol/SPEC_PATCH_WORDING.md). It uses the same parser and appliers as
`apply_patch`, including ordered stacked `@@` anchors, the same `reference` trigger for a single
corrective retry, and the fixed pipelines `reference` and `fuzzy + retry`. Neither patch format
uses LLM merge. Its 180 generation requests are additional to the original 1,260.

Added `reference, @@ in context` as a deterministic merge method for both patch formats after
these partial results were seen. It first tries the unchanged forward reference search. Only
when that fails and the anchor occurs in the chunk's old lines does it search from the anchor's
position minus the number of old lines before the anchor's first occurrence, bounded by the
current cursor. It writes supplied context exactly as `reference` does. This is an analysis
amendment based on observed failures, not a method fixed before collection.

The original `apply_patch` prompt and `reference` results stay in the study unchanged. Existing
generation, retry and merge requests retain their protocol, prompts, settings and cache keys.

## 2026-10-30: Amendment 2 (after all 1,260 generation replies, before retries and merges)

The original 1,260 generation replies showed diffs with a missing final blank context line:
the hunk then has one fewer line than its header declares. GPT-6.1 Sol's reply for
`2026-21949_one` is one example. The Python pre-filter rejected these hunks before invoking
either native tool. Strict `git apply` also rejects that example with `error: corrupt patch at
line 11`, while GNU `patch` and `git apply --recount` apply it. Rebuilding parsed hunks also
restored blank context markers that the model had omitted. These behaviours measured the
Python parser rather than each tool's handling of the reply.

Native appliers now receive the reply's raw hunk text. Only the surrounding wrapper/prose and
file headers are handled, with paths fixed to `a/document.md` and `b/document.md` and
`diff --git`/`index` lines dropped. Hunk counts, blank markers and trailing lines are not
repaired or re-serialised. The tools' own diagnostics and reject files determine per-hunk
outcomes. After a fatal whole-diff error without usable per-hunk results, each raw hunk gets
a separate cumulative native invocation. Failure details quote trimmed native error lines.
Added the deterministic method `git apply --recount` immediately after `git apply`, after
generation results were seen. Strict `git apply` remains the trigger and applier for udiff
corrective retries. No retry responses had been collected when this amendment was specified;
the error messages in their prospective prompts may therefore change.

The rename task `2026-21300_rename` asks for every occurrence of `ORV` to become `ORA`.
Its original expected document changed 16 singular occurrences but left 23 occurrences of
`ORVs`. Every model, including all full rewrites from GPT-6.1 Sol, Claude Sonnet 5.5 and Claude
Haiku 5.5, changed these to `ORAs`; seven paragraphs were consequently counted as collateral
under the old answer. The amended rule matches a whole-word base or a base followed by a
lowercase `s` and then a non-alphanumeric character or the end. It replaces the base and
keeps the `s`. The task and check now count 39 occurrences. The instruction text is unchanged.
No other rename task has a suffixed form: COTP, RB, IRS, DOE, RFA, FR, FEVS and ACF have none.
Other words (`IRFA`, `FRFA`, `CFR`) and `%20FEVS%20` inside a URL stay unchanged.

Only that task's expected document, check, occurrence count and expected hash changed.
All other 35 expected documents remain byte-identical, as asserted during migration and
comparison. The previous answer is preserved at
[expected_v1/2026-21300_rename.md](expected_v1/2026-21300_rename.md), and both answer versions
are covered by the frozen manifest. `rename_rule_comparison(merges)` reports exact counts
per format and method under both expected documents.

`exact` remains the primary document measure. Added `exact_nonblank`, which compares the
normalised documents after dropping blank lines entirely. Some otherwise wrong documents
omit a blank line before an inserted or moved paragraph; Markdown then joins it to the
paragraph above. Results are reported both with and without blank lines. Format and method
summaries include the secondary count/rate, and `near_misses(merges)` counts readable wrong
documents that pass it for each fixed format/pipeline. Unreadable replies cannot pass either
measure. This is a secondary analysis added after the generation replies were seen.

Addendum, same day, after the 180 `apply_patch_openai` generation replies and before any retry:
`git apply` rejected correct diffs from Claude Sonnet 5.5 with `error: corrupt patch at line 11`
because the reply's last line had no terminating newline (chat replies usually end without one).
GNU `patch` accepts such a file. The patch file handed to both native tools now ends with a
newline when the reply does not, as a text file written from the reply would. Hunk bytes are
otherwise unchanged. This changes `git apply` outcomes, and therefore which udiff replies get a
corrective retry; no retry had been collected.

The amendment leaves every generation and merge request unchanged. Before editing,
[check_amendment2.py](protocol/check_amendment2.py) froze all 36 x 8 x 5 generation keys,
the merge keys implied by complete cached generation replies and a fixed read-only cache
snapshot. Before/after comparison asserts the same keys despite later collection appends.
The oracle, raw-byte and cumulative native-tool tests, rename boundary checks and synthetic
analysis tests were extended offline. No model was called; the amendment did not write the
collection caches or `data/results/`.

## 2026-10-30: Amendment 3 (after the generation replies and retries, while the LLM merges were collected)

The rename task `2026-22093_rename` asks for every occurrence of `FEVS` to become `FEVA`.
The document includes the link
`https://www.opm.gov/chcoc/transmittals/2025/Memo%20on%20FEVS%20ReportsFINAL.pdf`.
The existing whole-word rule excludes its abbreviation because the `0` of `%20` immediately
precedes `FEVS`. Of the 40 generation replies (eight formats and five models, each applied
with the format's last-listed deterministic method), 24 also renamed this link occurrence.
Twelve of those would otherwise be exact. Only three replies were exact under the primary
answer. Literal compliance with "every occurrence" permits changing the link; preserving it
keeps its original address. Both readings are accepted after these replies were seen.

Added [expected_alt/2026-22093_rename.md](expected_alt/2026-22093_rename.md), which differs
from the primary expected document only by `%20FEVS%20` becoming `%20FEVA%20` in that link.
Only this task has `accepted_alternatives` metadata (file name and SHA256). The alternative
and updated task file are covered by the frozen manifest. All 36 primary expected documents,
instruction text and individual edit checks stay unchanged, including the whole-word rename
check. Every generation, retry and merge request key is preserved.

Scoring compares each output with the primary and each accepted alternative, choosing exact
first, then exact with blank lines removed, then fewer collateral paragraphs, and finally
the primary answer on a tie. `matched_answer` records the selected file name or `primary`.
All document scores and collateral measures refer to that same answer; edit checks are shared.
Unreadable outputs remain unreadable. Results are reported under both the primary-only and
accepted-alternative rules with `link_rule_comparison(merges)`. The existing plural-rule
comparison remains available. `rename_corrections_comparison(merges)` puts both corrections'
exact-count changes together, one row per format for a fixed pipeline (forgiving by default;
strict can also be requested), across all rename tasks. These are corrections chosen after
observing generation outputs, rather than rules fixed before collection.

The oracle now constructs replies from both FEVS answers and requires every deterministic
method to reproduce each exactly. Synthetic scoring and analysis tests cover answer selection,
both link readings, blank-line-only errors, collateral, unreadable outputs, retry and merge
provenance, and reconciliation of the compact comparison with the primary scores.
[check_amendment3.py](protocol/check_amendment3.py) freezes complete live-cache records by key
before editing and verifies all request hashes afterward, independent of later live appends.
The owner's Claude concurrency of 12, native patch final-newline handling and $0.50 Haiku cost
reservation are preserved. No model is called and no collection cache or `data/results/`
file is written by this amendment.

## 2026-10-30: collection record

All calls were collected on 30 October 2026 between 01:29 and 04:19 (UTC-4), in five runs of the same script that
reuse the caches; no cached reply was ever replaced.

- Before the run, three calls checked the CLI settings (a custom system prompt for `claude -p`, and
  `-c instructions=...` replacing Codex's own instructions, which `model_instructions_file` also achieves). Ten
  generation requests were sent as a live check (all five models on `2026-21949_one` as SEARCH/REPLACE and on
  `2026-22093_one` as whole documents); their replies are the cached generation replies for those requests.
- Run 1 collected the 1,260 generation replies of the seven original formats and was stopped as soon as generation
  finished, before any retry, so that amendments 1 and 2 could take effect. Run 2 collected the 180
  `apply_patch_openai` replies and was stopped at the same point for the final-newline addendum. Run 3 collected all
  439 retries and the first 78 LLM merges.
- Run 3 was stopped and restarted (run 4) with Claude concurrency raised from 6 to 12 to speed up the merges; the
  in-flight merge calls were lost and re-sent. Run 4 stopped when the Claude budget guard refused new calls: it
  reserves the CLI's $3 per-call cap for every call in flight, and twelve reservations plus $46.82 of actual spend
  exceeded the $80 cap. The reservation for Claude Haiku 5.5 calls was lowered to $0.50 (their actual cost was about
  $0.004 per merge), with the cap unchanged, and run 5 collected the remaining merges. None of these changes alters a
  request or its cache key.
- Totals: 1,440 generation replies, 439 retries and 525 merges (2,404 calls). No generation or retry call failed in
  transport; one merge call failed four times and is cached as an error. Claude list price $51.91 (Sonnet 5.5
  $42.33, Haiku 5.5 $9.59 including $5.46 of merges); OpenRouter $7.17 (Qwen3.8 27B $6.14 on Near AI FP8, DeepSeek
  V4.1 Flash $1.03 on DeepInfra FP8); GPT-6.1 Sol under a Codex subscription, 6.6 million input and 1.2 million output
  tokens.
